The console at `/pro/health` uses reported publication results. A Pro workflow can send an OIDC-authenticated report to `/api/pro/telemetry` after rendering. The report contains run status, duration, profile slugs and failed external asset URLs when available. It does not probe each README image request.

## Reading the score

The implementation groups render counters by **UTC calendar day**. The current score is successful recorded renders divided by all recorded renders for today, rounded to a percentage. The render total named `totalRenders24h` uses today's UTC bucket, not a rolling 24-hour window. Account-level `errorsLast24h` separately filters unresolved incidents by their last-seen time; the per-profile field counts unresolved incidents without that time filter.

| State       | Account-level interpretation                                       |
| :---------- | :----------------------------------------------------------------- |
| Operational | Recorded success rate at least 98% and no active errors.           |
| Warning     | No samples, any active errors, or recorded success rate below 98%. |
| Failed      | More than two active errors, or recorded success rate below 90%.   |

The no-sample score is currently `0` with a warning state. It means **no measured success rate**, not measured zero uptime. Per-profile failure thresholds differ: more than one active error can mark a profile failed.

The endpoint counts `published` and `svg_unchanged` as successful statuses only when there are no reported errors. A reported `skipped_stale` is currently counted as a failed render even though it can be normal concurrency protection. The Action exits on `skipped_interval` before sending a health report. A run-level error flag can affect every profile in the same report.

“Widget health” rows currently summarize each profile's artifacts; they are not independent probes of every widget. Failed URLs receive generic external-asset labels. A displayed last-render time can fall back to the profile's stored update time.

## Health badge

```markdown
![GitAscii publication health](https://gitascii.com/api/USERNAME/health-badge)
```

This is a separate, public GitAscii endpoint that summarizes account health across profiles. It remains valid in V2; the normal profile SVG is still served by GitHub. The badge is distinct from the [analytics badge](/pro/telemetry-and-privacy) and does not count visits.

The response requests a shared cache lifetime of 120 seconds with 300 seconds of stale-while-revalidate. If the health lookup throws, the route retains its initial “Operational / 100%” fallback; do not use the badge alone as an availability guarantee.

## Simulator and missing reports

The health simulator writes incidents and failed-render telemetry to the **same account stores** used by the dashboard. It is not an isolated dry run. Resolve simulated incidents in the errors console afterward; the recorded daily counters remain.

Reporting is best effort. Missing reports may mean telemetry is disabled, OIDC permissions are missing, or the report failed, even when the images were committed successfully. Diagnose publication in the repository's Actions log first. See [Action configuration](/guides/github-action) and [error monitoring](/pro/error-monitoring-and-alerts).

title: 'Custom Widget Development'
description: 'Add a renderer to a GitAscii checkout and include it in publication'
---

A custom widget is repository code returning SVG fragment markup. It is not a runtime plugin installed into the hosted app by uploading a configuration.

## Implement and register a renderer

```typescript
import { registerWidget } from '@/engine'
import { escapeXml } from '@/engine/core/xmlUtils'

registerWidget('custom-status', (widget, _data, styles) => {
  const message = escapeXml(String(widget.config.status || 'Building in public'))
  const color = escapeXml(String(styles.textColor || '#ffffff'))
  return `<text x="24" y="40" fill="${color}" font-family="monospace" font-size="16">${message}</text>`
})
```

The signature is `(widget, data, globalStyles, forceStatic?) => string`. Escape user-supplied text and attribute values, keep coordinates relative to the widget, and let the shared wrapper position it. If your renderer animates, honor `forceStatic` where applicable.

## Include it in both runtimes

`registerWidget` affects only the process where it runs. For a permanent built-in widget, add the identifier in `src/constants/widgetIds.ts`, register the renderer in `src/engine/core/WidgetRegistry.ts`, and add the appropriate editor catalog/property controls. The editor catalog is defined under `src/constants/widgets.ts`.

Backend publication and the GitHub Action must both include the new renderer. Rebuild the Action using `npm run build:action` when changing its bundled engine. A JSON file referring to an unknown widget ID does not load code; the registry renders a fallback label instead.

Use a one-widget configuration with `renderSvg` to generate a complete image. `renderWidgetSvg` alone returns a fragment. Follow the [local rendering example](/guides/reproduce-editor), then check dark/light output and any external-asset processing.
